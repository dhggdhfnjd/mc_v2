2Busia 場景與五個設計推論

你指定的 J-PAL 評估是 Eleanor Wiseman 和 Elisabeth Sadoulet 在肯亞西部 Busia 做的隨機對照試驗，合作方是 Sauti East Africa。先把數字放在一起：

項目數字
樣本1,100 位小規模商販。多數是來自鄉村、正式教育不多的女性；80% 賣農產品；55% 做跨境，其中 63% 走非正式通道
資訊缺口不知道官方口岸到底要繳多少稅；不知道哪個市場買最便宜、哪個市場賣最好
介入Sauti 平台（撥代碼的 USSD 文字選單）：東非各市場價格、正式口岸應繳稅額、匯率、天氣。59% 的人至少用過一次
利潤+17–18%

沒有改變的索賄和貪腐程度沒有變化

對設計的五個推論

  1. 錢是從「換市場、換品項」賺到的。利潤上升伴隨的是買賣市場數和品項數增加。所以「去哪賣」必須是一等功能。你們在 D8 講的泡泡地圖正好打在這個機制上，我把它從附加頁升成主流程的一個出口。
  2. 資訊沒有減少索賄。別把反貪當賣點。口岸免稅規則（STR）我只做成一張知識卡，效果誠實標「未知」。
  3. 使用者是教育程度不高的女性小商販。圖示優先、數字優先、Kiswahili、盡量不打字。你要的拍照辨識和九宮格數字直選都是為她們設計的。
  4. Sauti 已經把「查價」做完了，而且是純文字。再做一個查價工具沒有差異。我們的差異是把價格變成三個答案：這一批該收多少、對方開的價能不能接受、不接受還能去哪賣。再用成交價回流去補官方資料沒有的市場。
  5. 她們是商販，不只是農夫。在邊境一邊買、到另一邊賣。所以買進和賣出兩個角色都要支援，肯亞先令（KES）和烏干達先令（UGX）要能互換。

4算錢與議價引擎

這一節回應你說的「在實際算錢或討價還價的時候有幫助」。整個引擎是一包沒有副作用的純函式（packages/money），全部用整數的最小幣值計算，前端和後端共用同一份程式，所以手機上算出來的數字和伺服器驗證的數字一定相同。這裡面不放任何 AI：錢的計算必須每次都一樣、能寫測試、能解釋。

在地單位 補充

官方價是每公斤，但市場上沒人用公斤講價。玉米論 90 公斤的袋、約 2 公斤的罐（肯亞叫 gorogoro）、約 17 公斤的桶（debe）；番茄論木箱；matooke 論串。目錄裡每個品項帶一張單位換算表，S4 標題列那行「2 bags × 90 kg」就是它算的。換算值要田調校準 待驗證。

雙幣與換匯損失 補充

所有金額都能按 # 在 KES 和 UGX 之間切換，匯率用中間價。使用者可以打進邊境換匯攤報給她的匯率，畫面直接顯示「這個匯率讓你少拿 UGX 12,000（−2.1%）」。換匯本身也是一場議價，J-PAL 的介入裡就包含匯率資訊。

買、賣兩種角色 補充

賣的時候對方出價越高越綠，買的時候越低越綠。同一套公式，方向相反，進 S4 時用左右鍵切換 Sell／Buy。

公平區間 D3 D14

以官方價為錨，回報價只能在錨附近修正，這是照 D14「以 Government 為主」。

回報夠（信心 ≥ 2 格）：
  區間 = 回報價 P25–P75，
         夾在官方價 ±20% 以內
回報不夠：
  區間 = 官方價 × (1 ± v)
  v = 近 30 天波動，最小 5%、最大 15%
品質：乘上該品項的等級係數
      （例 Grade 2 = 0.90）

成本底線 補充

底線/kg = (進貨 + 路費 + 市場規費
           + 口岸費用)
          ÷ (數量 × (1 − 損耗率))

底線高過區間上緣時，不叫她硬撐，直接提示「這個市場回不了本，看看別的市場」，連到 §5。

對方每喊一次價，畫面回答四件事 補充

回答規則（以賣方為例）畫面
能不能接受出價 ≥ 參考價：綠。落在公平區間下半：黃。低於區間：紅整條色塊，字大
差多少錢（出價 − 參考價）× 數量，講整批的錢，不講百分比「you lose 1,400」
該還多少對等讓步：開價設在公平區間上緣再高一點；對方每從亂喊價往市價靠近一步，我就從開價往市價退同樣的比例，兩邊在市價碰頭。對方亂喊價就一步不退，永遠不低於成本底線。結果取成講得出口的整數。這條是實作時改的：原本的公式在單元測試裡被抓到「對方加價、我的要價反而上升」「Ask 4,950」
不賣還能去哪從需求看板和其他市場找淨價最高的替代方案：對方價 − 路費 − 口岸費用 − 損耗「Or: Bungoma net +360」

第四行是整個設計的關節：你們的需求地圖（D7、D8）不只是找買家的地方，它同時是議價桌上最硬的籌碼。談判裡最有力的一句話永遠是「別人出得比你高」，而這句話現在有數字撐著。

另外兩個小東西。一句話術：還價旁邊給一句照模板填數字的 Kiswahili，例如「Bei ya soko leo ni shilingi 55 kwa kilo.」（今天市價每公斤 55 先令），模板要請母語者校過 待驗證。找零：成交後輸入對方給的鈔票面額，算出要找多少，見 S5。

5需求看板與泡泡地圖

需求貼文 D7

照 D6 的結論，不碰物流和金流，只做撮合。買家貼一則需求，賣家自己決定要不要送過去。

欄位說明
品項、等級沿用目錄
數量、單位例 500 kg 或 6 袋
願意收的價格、幣別每公斤或每單位，後端一律換成每公斤存
交貨市場只到市場層級，不收住址。這裡治安不好，公開「某人在某地址等著收 500 公斤貨」等於幫搶匪指路 補充
有效期1、3、7 天，到期自動下架
聯絡方式公開號碼，或只走簡訊中繼（見下）

買家多半是磨坊、學校、餐館、批發商，手上有智慧型手機。所以貼需求這一頁同時做成響應式網頁，同一份前端在智慧機上就是 PWA（§9）。按鍵機上也能貼，只是欄位一頁一個。

每一則需求的出價也會進價格引擎，當成權重較低的「買方出價觀測值」。這就是錄音裡講的「順便整理出市場價格」。

排序看淨價，不看標價 D8

錄音 93 說的是「看他的路費，或是看他的價錢哪一個比較好」，兩件事合起來就是淨價：

淨價/kg = 對方出價 − 路費/kg(我的地區 → 對方市場) − 口岸費用/kg − 出價 × 途中損耗率

路費先用 routes 表的估計值（市場兩兩之間每袋多少錢），使用者可以改成自己實際付的。成交回報時順手問一句「路費付了多少」，路費表就會越來越準 補充。

泡泡地圖在按鍵機上怎麼操作 D8 補充

  • 走廊示意圖，不是可拖曳地圖。Busia 走廊大約十二個市場節點：烏干達側 Kampala、Jinja、Iganga、Tororo、Mbale，肯亞側 Bungoma、Kakamega、Kisumu、Eldoret，Busia 壓在邊境線上。節點在螢幕上的位置預先畫好，存在 markets.map_x / map_y。
  • 泡泡編碼。大小是需求量（半徑正比於數量的平方根），編號是淨價排名，顏色分「比在本地賣好」和「比較差」兩種。
  • 方向鍵在泡泡之間跳。每個節點預先定好上下左右的鄰居，不做即時幾何運算，所以行為完全可預期、可測試。也可以直接按泡泡上的數字。下方兩行永遠顯示目前泡泡的出價、數量、淨價。
  • 為什麼用 SVG。Cloud Phone 傳給手機的是向量繪圖指令，不是像素。圓、線、字這種向量圖形傳起來便宜，地圖圖磚是點陣圖，又貴又糊。整張圖一次畫完，不做冒出動畫：官方文件說畫面更新最快每秒 20 格，而且每一格都走使用者的流量 實機量流量。
  • 128×160 的機型放不下地圖，自動改成依淨價排序的清單。

雙方怎麼聯絡 補充

錄音沒談到這一段，但沒有它撮合就斷了。限制是：tel: 連結要 Cloud Phone client 3.1.2 以上，測試機 itel R60+ 是 2.5.0，點不了。

  1. 先用 navigator.hasFeature('TelScheme') 偵測，支援就給撥號連結。
  2. 不支援：大字顯示號碼，加一個「SMS me this contact」。伺服器把買家號碼和需求摘要用簡訊寄到賣家手機，她從簡訊收件匣就能直接回撥。
  3. 買家選「不公開號碼」時走中繼：賣家按「我有興趣」，買家收到一封帶賣家號碼的簡訊，由買家回撥。

假需求怎麼辦 補充

回報價格可以匿名（§7），但貼需求不行：假需求會讓人白跑一趟，代價是真的路費。所以貼需求要先用簡訊驗證碼綁定電話號碼，反正聯絡本來就需要號碼。貼文到期後兩邊各問一句「有成交嗎」，算出這個買家的履約率，顯示在貼文旁邊。履約率太低的貼文排序往後。

6拍照辨識

你要的「不一定要手動輸入，拍照就知道是什麼」。先講限制，因為它決定了設計：

  • 測試機 itel R60+ 的相機是 0.08MP，大約 320×240 像素。分得出番茄和洋蔥，分不出等級。所以拍照只辨識品項，等級用三張示意圖手選。
  • Cloud Phone 的上傳是 <input type="file" accept="image/*">，會開一個原生的全螢幕檔案挑選器（Phone／MemoryCard）。能不能直接開相機要看機型；不能的話，使用者得先用相機 App 拍好再回來選 待驗證。模擬器測不了上傳，只能在實機上試。
  • 結論：拍照是一條捷徑，永遠不是唯一的路。九宮格一直都在。
  1. 偵測navigator.hasFeature('ImageUpload') 為真，S1 的左軟鍵才顯示 Photo；否則顯示 Search。
  2. 選圖與縮圖widget 拿到檔案後畫到 canvas，縮到長邊 512px 以內、JPEG 品質 0.7，拿掉 EXIF。這一步跑在 CloudMosa 的雲端瀏覽器裡，不吃手機效能。
  3. 送辨識POST /v1/recognize。Worker 先查每台裝置每日上限，再算影像雜湊查快取，同一張圖不付第二次錢。
  4. 視覺模型，輸出鎖在目錄裡提示詞帶整份品項目錄（ID、英文名、Kiswahili 名、外觀提示），用 tool use 的 JSON schema 把答案限制成目錄 ID 的 enum 加上 unknown，回前三名和信心值。模型藏在 VisionProvider 介面後面，起步用 Claude Haiku 4.5（claude-haiku-4-5-20251001），便宜、快、看得懂圖；之後可以換。
  5. 人來確認畫面列三個候選，按 1、2、3 確認，按 0 回九宮格。第一名信心低於門檻，或回 unknown，就直接落到九宮格，游標停在最可能的那一類。
  6. 學習迴圈記下「模型猜的」和「使用者最後選的」。使用者同意才把縮圖存進 R2。累積到幾千張之後訓練一個小型分類器接手，視覺模型退成後備，單次成本降到接近零。

成交照片（D13）走同一條路。S5 的左軟鍵可以補一張貨的照片，kind=proof。模型只檢查一件事：照片裡是不是他聲稱的品項。通過的回報權重乘 1.5。它擋不住有心造假的人，但能拉高大量灌水的成本，所以是加分項，不是門檻。驗完只留雜湊，不留照片。

7回報可信度：把未決的爭論定案

錄音最後一分半在爭這件事，沒有結論。我整理一下各方說的：以官方價為主（D14）；成交後拍照（D13）；信用分（D15）；參考 App 的 AI confidence（D15）；身分認證難做，而且認證了還是能亂報（D15）；怕一筆假資料就把價格搞爛（D15）。

我的建議是五道防線，全部不需要身分認證，和你們的直覺一致：

  1. 官方價錨定 D14官方價永遠顯示在最上面。回報低於官方價一半或高於兩倍，直接拒收，「可可一口 1000」死在這一關。偏離超過 ±20% 的先隔離、不計入（以官方價或現有回報中位數為中心，兩者取寬），48 小時內要再有 2 位獨立回報者落在它 ±10% 以內才放行。真的行情劇變會有人跟著報，過得了；一個人亂報過不了。
  2. 用中位數，不用平均 補充顯示的是加權中位數和 P25–P75。中位數要超過一半的權重是假的才會被帶走，「一筆就搞爛」在數學上做不到。
  3. 一人一票，會過期 補充同一台裝置對同一個「品項＋市場」，24 小時內只算最新一筆。權重每 3 天減半。7 天內不到 3 位獨立回報者就不顯示回報價，只顯示「回報不足，成為第一個」。
  4. 信用分看行為，不看身分 D15新裝置權重 0.3，上限 1.0。每一筆落在最終 P10–P90 以內的回報加 0.05；被拒收的扣 0.15；先被隔離、後來證明是對的加 0.1，獎勵最早報出真實變化的人。走完 S4→S5 成交流程產生的回報乘 1.2；照片驗過的乘 1.5（D13）。使用者看到的只是自己的星星數。
  5. 信心格 D15這就是你們看到的「AI confidence」的對應物，但它是統計算出來的，不是模型猜的：3–4 人或最新一筆超過 4 天，一格；5–9 人，兩格；10 人以上且離散度（IQR÷中位數）在 10% 以內，三格。

買方想把價格報低、賣方想報高，兩邊的偏誤方向相反。每筆回報都帶著 buy／sell，聚合時兩邊各自取中位數再合併，任何一邊人多都不會把價格拖走 補充。

8系統架構總圖

先講一個和一般網頁 App 不一樣的前提：Cloud Phone 的瀏覽器跑在 CloudMosa 的機房，手機只送按鍵、只收繪圖指令。所以我們的「前端」其實在雲端執行，它和我們 API 之間的網路很快；真正又慢又貴的是手機到機房這一段。整個架構都圍繞這件事：每個畫面只打一次 API，畫面能不動就不動。

為什麼選這一組

  • Workers 放在邊緣。官方文件列的 Cloud Phone 機房是新加坡和美國為主、南非和西班牙為輔。東非使用者的雲端瀏覽器會落在哪一座要實測；API 放 anycast 邊緣，不管落在哪座都打到最近的節點 待驗證。
  • 讀寫分開。讀價格只碰 KV 裡算好的快照，一次往返。寫入（回報、成交、照片）先進 Queue 再慢慢算信用和聚合，使用者不用等。
  • 全部 serverless、用量計費。學生團隊零維運，比賽期間幾乎不花錢。
  • 同一份前端兩種身分。按鍵機上是 Cloud Phone widget，智慧型手機上是可安裝的 PWA。題目說這是「第二支手機」，同一個人的第一支手機也能看同一本帳。

四條前端規矩

  1. 一個畫面一次請求。GET /v1/prices 一次把官方價、回報價、信心、7 日走勢、匯率全帶回來，S3、S4、Show card 都用這一包。
  2. 畫面省著動。不用 CSS 動畫和 transition，不放會轉的載入圖示（用靜態的「Loading…」），不設自動重新整理的計時器。圖示用內嵌 SVG，不用點陣圖。
  3. 能力先偵測再顯示。ImageUpload、TelScheme、SmsScheme、Vibrate 都先問 navigator.hasFeature()，沒有就連按鈕都不出現，不讓使用者按到沒反應的東西。
  4. 算錢在本地。價格抓回來之後，數量、出價、還價全在 widget 裡算，打數字不發請求，反應是即時的。

身分。第一次開啟時呼叫 POST /v1/devices 拿一個簽過的匿名裝置權杖，存 localStorage。不用註冊就能用全部查價、算錢、回報功能。要貼需求、要收簡訊、或換手機想把帳本帶走，才用簡訊驗證碼綁定電話號碼。Cloud Phone 官方也建議重要資料要讓使用者登入並備份到帳號。

語言。英文和 Kiswahili 起步，之後加 Luganda。字串保持短，數字和幣別用 Intl.NumberFormat。

12容錯與邊界情況

狀況系統怎麼做
我們的 API 逾時或掛掉顯示 localStorage 裡同一個（品項、市場）上次的回應，標「Last updated 18 Sep 06:10」。計算機和議價照常能用，因為它們在本地算
官方價超過 3 天沒更新日期變色標「old」，公平區間自動放寬。價格旁邊永遠有日期，這條不能省
這個市場沒有官方價用最近的有官方價的市場，加上兩地歷史價差，標「estimated from Bungoma」
回報者不到 3 人不顯示回報價，顯示「Not enough reports. Be the first.」
機型不支援圖片上傳，或辨識信心低左軟鍵改成 Search；辨識失敗直接落到九宮格
POST 送到一半斷線widget 帶同一個 Idempotency-Key 重送，伺服器去重
佇列消費者失敗重試 3 次後進死信佇列。帳本已經先寫好了，使用者不受影響
手機完全沒訊號Cloud Phone 沒有離線模式，畫面會停住，這是平台限制。對策是出門前按「SMS me this card」，把今天的價格卡寄到簡訊收件匣，在市場裡沒網路也看得到
128×160 的小螢幕地圖改清單、九宮格改單欄、字級照官方指引降到 12pt
視覺 API 費用暴衝每台裝置每日上限、相同影像雜湊快取、全站每日預算熔斷後自動停用 Photo 鍵
隱私核心功能不收任何個資。電話號碼只存加鹽雜湊，另存一份加密的給聯絡中繼用。回報價要滿 3 人才顯示，避免從單筆資料認出人

14里程碑、待驗證、與現有原型的銜接

拿到測試機當天先驗五件事

  1. hasFeature('ImageUpload') 的結果，以及檔案挑選器能不能直接開相機。這決定 §6 的體驗。
  2. LSK 是不是 Escape、RSK 是不是觸發 back 事件。
  3. * 和 # 的 event.key。
  4. 16px 的 Roboto Condensed 在實機上讀不讀得清楚。
  5. API 日誌裡 X-Forwarded-For 的樣子，以及從雲端瀏覽器到 Workers 的延遲。

還沒確認的事

  • Cloud Phone 在肯亞已上市但基數小，烏干達是否上市未確認。主要人物設定放在肯亞側的 Busia 商販比較穩。
  • R60+ 這支測試機本身賣在越南、孟加拉、巴基斯坦，不在東非。
  • KAMIS 的抓取方式與條款、烏干達日價來源、單位換算值、Kiswahili 話術。

三階段切法

  1. 核心迴圈。S1 到 S5、官方價（KAMIS＋WFP）、議價引擎、帳本、Report、§7 的聚合。做完這階段就已經是一個完整可上線的 App。
  2. 去哪賣。需求看板、泡泡地圖、淨價排序、History、Season。
  3. 加分。拍照辨識、成交照片、簡訊側通道、Border & FX 卡、Kiswahili。

Demo 腳本

兩支手機並排。買家在 Bungoma 貼「玉米 500 kg、每公斤 60」。賣家在 Busia 的地圖上看到 1 號泡泡冒出來，回到攤位前，對方開 8,500，畫面亮紅燈、建議還 10,100、旁邊寫著 Bungoma 淨賺多 360。最後 9,700 成交，按 Save，另一支手機上的回報價跟著動。整條資料迴圈在兩分鐘內演完。

和 farm-price-mvp「賣不賣？」原型的銜接

資料夾裡那份單檔原型有四樣東西可以直接沿用：九宮格數字直選、報價檢核量表、扣運費後的淨收益比價、回報加星。要改的有四處：

  1. 軟鍵對應反了。原型把 Escape 當右軟鍵的「返回」。官方文件是 LSK＝Escape，RSK 觸發 back 事件。照原型的寫法上實機，按左軟鍵會變成返回。
  2. 拿掉 pulse、bounce 和 transition 動畫。每一格動畫都是一次畫面更新，走的是使用者的流量。
  3. 資料換成 Busia。現在是奈及利亞的 ₦、Kano、Lagos，換成 KSh／UGX 和走廊上的市場。
  4. 補上討論的主流程。Area、數量試算、成交回報進帳本、需求地圖、Season。
